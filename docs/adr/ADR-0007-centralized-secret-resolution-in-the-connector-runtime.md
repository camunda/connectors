# ADR-0007: Centralized Secret Resolution in the Connector Runtime

## Status
Accepted

## Context

[PDP-3040](https://github.com/camunda/product-hub/issues/3040) adds a new way to write secrets in a process: `camunda.secrets.<name>`. Values come from secret stores configured on the broker, and two new endpoints read them: `POST /v2/secrets/resolve` and `POST /v2/secrets/list`. In time this is meant to replace the way the Connector Runtime handles `{{secrets.X}}` and bare `secrets.X` today. [#8222](https://github.com/camunda/connectors/issues/8222) tracks the work on the connectors side.

Twelve constraints shape the decision.

1. **For jobs, the engine resolves these secrets itself.** It replaces the placeholder in a job's variables before the job is marked activated. Today that covers jobs a worker asks for; `camunda/camunda#56564` extends it to jobs the broker pushes, targeted at the same release. Job push was named in the epic's own phase-1 criteria from the start — long polling simply shipped first.

2. **Nothing resolves them anywhere else.** Inbound connectors have no job, and out-of-band configuration validation runs outside any process, so neither is covered now or after that work lands.

3. **`camunda.secrets.<name>` is a FEEL expression; `{{secrets.X}}` is text the engine ignores.** The authoring form is the bare path written as an expression, `=camunda.secrets.NAME`, which the engine evaluates into placeholder text and substitutes later. Being FEEL, the name has to be written as FEEL reads it: a name containing a dash is authored backtick-escaped, ``=camunda.secrets.`db-password` ``, because a bare dash is the minus operator. The two forms are therefore not interchangeable in a model, and anything that generates input mappings or element properties has to know which it is emitting.

4. **The runtime replaces legacy secrets one name at a time, and the new endpoint wants them in groups.** Legacy replacement runs over the request as serialized JSON, before it is bound to objects, calling a single-name lookup for each match. The resolve endpoint takes a batch of references and caps how many one call may carry. So treating the cluster as one more `SecretProvider` would mean one HTTP request per secret, and the existing `SecretProvider.fetchAll` cannot help: it returns values without saying which name each belongs to.

5. **The resolve call carries no tenant** — the cluster derives it from the caller's token. The only routing question is therefore which `CamundaClient` to call, not how to describe a tenant.

6. **The runtime's pattern for the old form overlaps the new one.** `SecretUtil.SECRET_PATTERN_SECRETS` matches the `secrets.<name>` part inside `camunda.secrets.<name>`. The same method that finds those names, `retrieveSecretKeysInInput`, also builds the outbound allow-list of declared secrets, so any change to what it matches changes what that allow-list permits.

7. **The engine rejects a reference written as a plain literal wherever one can be written.** `SecretReferenceLiteralValidator` covers `zeebe:input` sources and, since the engine work described under *Asks on the engine* below, `zeebe:property` extension elements — which is where inbound connector configuration lives. The bare form is therefore policed on the inbound surface too, not merely unpoliced.

8. **The expression-evaluation endpoint knows the new form.** The endpoint evaluates against the engine's placeholder-emitting context, so an expression naming `camunda.secrets.<name>` comes back with the reference text in the result rather than resolving to nothing. A reference survives evaluation, including one that is only part of a larger expression: `="Bearer " + camunda.secrets.TOKEN` evaluates to `Bearer camunda.secrets.TOKEN`.

9. **The evaluation response reports which references that evaluation used.** Alongside the result, the response carries the secret references the engine derived from the parsed FEEL expression and from the references stored on the `SECRET_REFERENCE` cluster variables the evaluation read. This is authoritative: it comes from the engine's own parse, not from scanning text.

10. **The engine records an expression-evaluation request and its result verbatim.** Whatever is sent as expression source, and whatever comes back, is persisted in the cluster. Substituting a secret value into expression source before sending it would therefore write that value into cluster storage.

11. **A cluster variable can carry references inside its value.** A cluster variable has a kind: `JSON` or `SECRET_REFERENCE`. A `SECRET_REFERENCE` one holds `camunda.secrets.<name>` text instead of a value, and the engine swaps in the real value at job activation. It only does that for variables of that kind — a `JSON` one is left alone even if its contents look like a reference. So a reference can reach the runtime as *data* that no model wrote.

12. **Without a rule of some kind, any text that looks like a reference would be resolved.** Verified against a live cluster: a `JSON` variable holding `{"note": "camunda.secrets.NOT_DECLARED"}` read back exactly that text through the expression endpoint. Anything scanning evaluated results for references would otherwise resolve a secret nobody declared — and the same applies to a webhook payload, an HTTP response body, or any other attacker-supplied text that reaches a connector property.

## Decision

Support `camunda.secrets.<name>` **for inbound connectors and configuration validation only**, substituting values into the result of a cluster expression evaluation, restricted to the references that evaluation reported. Leave job handling to the engine. The two forms of secret stay completely apart, and the public SDK does not change.

1. **Do not handle the outbound job path.** The engine owns job activation and is closing its remaining gap there in the same release (Context 1). Building our own would put two components in charge of the same thing, with different failure behaviour, for as long as it took. Adding the outbound path later, if that work slips, is a small change on top of what this decision already builds; removing it afterwards would mean deleting code other things had come to depend on. Inbound and configuration validation are the cases nothing else will ever cover (Context 2), and they are what this addresses.

   **Accepted risk.** Every Connectors bundle asks the broker to push jobs, which is the case the engine does not yet cover. If that upstream work misses the release, secrets in the new form will not work for outbound connectors until it does.

2. **Keep the two forms apart.** `camunda.secrets.<name>` is read only through the cluster's resolve endpoint; `{{secrets.X}}` and bare `secrets.X` are read only through the runtime's existing secret providers. Neither falls back to the other when it comes up empty, and the legacy form keeps working exactly as it does today. (Amended — see *Amendment 1* below, which allows a legacy name to fall back to the cluster's stores when a deployment asks for it.) They draw on different configuration — stores configured on the broker, against providers configured in the runtime — and letting an environment variable satisfy a reference written against a broker store would make it impossible to say where a secret actually came from.

3. **Resolution happens after evaluation, on the result — never before.** The engine records an evaluation request and its result verbatim (Context 10), so splicing a secret value into expression source would persist that value in the cluster. It would also be unsafe on its own terms: a quote or an operator inside a secret value silently changes what the expression means. The reference is therefore sent to the cluster exactly as the modeller wrote it, survives evaluation as placeholder text (Context 8), and the value is substituted into the result afterwards.

   The hook is `EvaluationResultProcessor` in `connector-feel`, applied by `CamundaClientFeelExpressionEvaluator` to the raw result of every evaluation before the result is converted to the caller's target type. Every public `evaluate` method funnels through one internal call, so a processor applies to all of them. `SecretResolvingResultProcessor` is the implementation, and `SecretReferenceResolver` is what calls the endpoint.

4. **The allow-list comes from the engine, per evaluation.** The evaluation response reports the references that evaluation actually used (Context 9). `SecretResolvingResultProcessor` builds its allow-list from that report alone, walks the result graph — maps, lists, strings — collecting only references the report names, and substitutes only those, only inside that one evaluation's result. Nothing is derived from scanning property text, and nothing is read from cluster-variable storage: the runtime makes no cluster-variable search call at all.

   Two properties follow, and both are the point. Text that arrived as *data* — a webhook payload, a plain `JSON` cluster variable — is reported by nothing and stays literal (Context 12). And because the list is scoped to a single evaluation rather than pooled across a whole property binding, reference-shaped text in one property cannot be substituted because a *sibling* property legitimately named a secret.

   The store id a report carries is informational — a reference never names a store — so two reports differing only in store id are one reference to resolve.

5. **A reference embedded in a larger expression is supported.** `="Bearer " + camunda.secrets.TOKEN` is not an edge case to be refused: it is the shape the engine built the feature around, and it is what `Bearer {{secrets.TOKEN}}` migrates to. Because the placeholder survives evaluation as text inside the result, and the allow-list is per evaluation rather than per property, this needs no special handling: the result string `Bearer camunda.secrets.TOKEN` is walked like any other and the reference inside it is substituted. Recognising a reference only as a whole property value is therefore not a constraint the runtime imposes.

6. **Two registration points, one substitution point.** A `@FEEL`-annotated property keeps the existing FEEL deserializer, because a property-level deserializer wins over a type-registered one. Every other string is covered by `SecretReferenceDeserializer`, registered for `String` by `JacksonModuleSecretReference`.

   The type registration is needed for two reasons. Eleven of the twenty-one inbound credential fields carry `@FEEL`; the other ten are plain strings, and a reference written in one of those has to resolve too. And a property-level introspector cannot reach the string values inside `Map` and `List` properties or values reached through a field declared as `Object` — an `Authorization` header is exactly where a secret goes.

   The deserializer is deliberately narrow. It acts only on a value written as an expression that names a reference (it checks for a leading `=` and the `camunda.secrets.` prefix), and only when the reader carries an evaluator of its own — which is how the runtime hands each connector context its cluster-backed one. The raw-property round-trip through legacy secret replacement carries none, and there the value must survive untouched. It supplies no FEEL context: the point is to resolve a secret reference, not to turn plain properties into expression fields.

   The module is registered on the inbound property-binding mapper only, and deliberately kept out of `JacksonModuleFeelFunction`, which is also installed on the outbound and Camunda client mappers where the engine does the substituting.

   **An evaluation result is data, never expression source.** Converting a result runs it back through the deserializers, and a string in the result beginning with `=` and naming a reference would otherwise be sent to the cluster as a *new* expression — and that second evaluation would legitimately reference the secret, so it would resolve. The per-evaluation allow-list of Decision 4 would never be violated; attacker-supplied text would simply have been laundered onto it, defeating Decision 4 entirely for anyone who can place text into data a property reads. The same path would re-evaluate a resolved secret whose value begins with `=`.

   **Which mapper binds a result settles this, rather than a rule applied while binding it.** A connector's properties are bound by the property mapper, which registers the FEEL and secret-reference modules. Values returned by an evaluation are bound by a second mapper, `FeelEvaluationResultMapper`, carrying the same base and document modules and neither of those two. Nothing in a result can be evaluated or resolved, because nothing that would do so is registered, and the invariant is checked by reading one wiring line rather than by tracing every path that evaluates.

   Two things travel on the result reader to complete that. The attributes of the binding that produced the value, because a result cannot always be bound without them — the document module resolves its factory per call from the physical-tenant attribute. And an evaluator that answers with the text of the expression, because `FeelDeserializer` is public and a model may name it directly with `@JsonDeserialize`, which registers it on any mapper binding that type: with the binding's evaluator it would resolve a secret from result text, and with none it would fall back to a local engine and run that text as an expression.

   Separate mappers also give each conversion its own deserialization context, which the deferred `Function`/`Supplier` properties require: they are bound once and invoked once per request — concurrently, for an inbound webhook — and Jackson's context does not support being shared that way.

   Three consequences follow, all deliberate. A nested `@FEEL` field inside a result is not evaluated; it binds as data. A `Function`- or `Supplier`-typed field inside a result does not bind at all, since a callback's source comes from the model. A wiring that supplies no result mapper falls back to a blank one, which binds plain data but materialises no documents.

   Both routes end in the same decorated evaluator, so there is exactly one place in the runtime where a secret value replaces its reference. It is installed on `InboundConnectorContextImpl`, on `DefaultProcessInstanceContext` (the path polling connectors bind through), and on the configuration-validation evaluators. The ambient evaluator is left alone.

7. **Fail closed: an unreported or unresolvable reference stays as it is.** `SecretReferenceUtil.replaceReferences` leaves a reference with no resolved value exactly where it is, so a placeholder never becomes an empty string, and the failure is reported against the reference rather than as an unexplained blank credential. When a result contains reference-shaped text that the report does not name, the text is left alone and one warning is logged for the lifetime of the runtime — not one per occurrence, and without repeating the text, which may be attacker-supplied. Two very different things reach that path: text that was never a reference, which is the defence working, and a cluster too old to report referenced secrets, where every reference goes unresolved. The client normalises an absent report to an empty list, so those two cannot be told apart at this layer; the single warning is what points at the second.

   This also keeps a refusal a refusal. The runtime already distinguishes a secret nobody can supply from one deliberately withheld: for the legacy form, a name the `SecretFilter` refuses is left in the text untouched. The new form behaves the same way by construction — a reference the cluster did not report is left in place rather than failing — although through a different mechanism: `SecretFilter` gates the legacy form only and is not consulted here.

   Replacement makes a single pass over the text, so a resolved value is never itself rescanned: a secret whose value contains reference-shaped text stays opaque. The pattern is greedy, so `camunda.secrets.TOKEN` cannot be substituted inside `camunda.secrets.TOKEN_V2`.

8. **Resolve in groups, and only when there is something to resolve.** All references found in one evaluation result are resolved in as few calls as the endpoint's limit allows — `SecretReferenceResolver` batches at twenty per request — rather than one at a time (Context 4). An evaluation that reports no references, or whose result contains none, does not call the cluster at all. That is what keeps this free for everything that does not use the new form.

9. **Keep the new resolver inside the runtime; do not extend the public SDK.** Because the two forms are kept apart, the resolver is never one of the secret providers, so widening the `SecretProvider` interface would add public API that nothing here uses. `SecretProvider` and `fetchAll` are left exactly as they are, and existing implementations — including other people's — keep working unchanged.

10. **Route by client, not by tenant** (Context 5). Inbound connector contexts are already created per physical tenant, so each already holds the correct client and builds its evaluator from it. Configuration validation keeps one evaluator per engine, each built with a resolver over that engine's client. No new way of describing tenancy is introduced, and the existing secret-resolution and secret-filtering context types are not merged.

11. **Treat every failure the same way, and log what it was.** All the failures the endpoint can report mean one thing here: no value, so the placeholder stays and the connector fails as it already does for a missing secret. There is no behaviour that branches on the reported cause. Because the endpoint answers successfully even when individual references fail, a missing grant would otherwise be indistinguishable from a misspelled name, so the reported cause is logged per reference. A network failure, or a cluster too old to have the endpoint, is treated identically — such a cluster degrades to "secret not available" rather than failing outright. The thrown exception itself is never logged, only its type: a client error message can echo the response body.

12. **Keep the two forms from overlapping in text, narrowly.** The legacy pattern gains a negative lookbehind, `(?<!camunda\.)secrets\.…`, so it can no longer match inside a reference of the new form (Context 6), and only for that prefix — the pattern still matches in other places it arguably should not, and changing that is a separate question. Without this the legacy pass, which runs first and over raw model text, would rewrite the tail of a new-form reference from a *local* provider: the wrong store, and the reference destroyed before the cluster ever saw it. Because the same method feeds the outbound allow-list, `retrieveSecretKeysInInput` is also taught to recognise the new form, so the set of secrets that list permits is unchanged for every existing process.

13. **Configuration validation resolves the new form only, and rejects the legacy syntax.** A `credentialRef` is evaluated on the cluster and its references are substituted by the same result processor, with the same per-evaluation allow-list. Legacy replacement is removed from that path entirely, and `ConfigurationValidationService` no longer takes a `SecretProviderAggregator`.

    This is the only place in the runtime where legacy replacement ran over a FEEL *result* rather than over raw model text, and the only one combining that with an allow-all filter. At that point nothing distinguishes a secret name a configuration declared from one that arrived as data, and out-of-band validation has no process or element scope from which to derive an allow-list — which is exactly what Decision 4 supplies for the new form and nothing supplies for the old one.

    A resolved configuration still carrying the legacy syntax is rejected rather than passed through, with a message naming the supported form: "The configuration uses an unsupported secret syntax. Reference secrets as `camunda.secrets.<name>`." Leaving the text in place would bind it as the credential and fail at the target with nothing to explain why. The message names only syntax, never resolved content, so it is safe to return under the endpoint's message-safety policy. The surface is unreleased, so there is no legacy behaviour to deprecate.

14. **Do nothing yet about hiding secrets from error output.** Values in the new form can only appear where this decision substitutes them, and the only place the runtime hides secrets from errors is on the outbound path, which this does not touch. Two gaps are recorded as separate work rather than addressed here: inbound has never hidden secrets from error output, and once the engine substitutes a value into job variables the reference is gone, leaving nothing for the outbound masking to recognise — which already applies today and needs information the job does not currently carry, so it belongs upstream.

15. **Accept that substitution within one evaluation is not positional.** If an expression legitimately references secret X, then any attacker-supplied text that lands in *that same evaluation's* result is also subject to X's substitution. This is not closable by position: the result of a transformed expression carries no pointers back into its source, so there is no way to say which span of the result came from the reference and which from data. The exposure is bounded — the attacker learns only a secret that the very expression they influenced already uses, and never one from another property, another evaluation or another element. Narrowing the allow-list further would not help, because the reference is genuinely on it.

**Asks on the engine.** All three asks recorded when this work started have been delivered, in [camunda/camunda#60240](https://github.com/camunda/camunda/issues/60240), [#60237](https://github.com/camunda/camunda/issues/60237) and [#60385](https://github.com/camunda/camunda/issues/60385): the placeholder-emitting context is installed on the expression-evaluation endpoint (Context 8), literal validation of the bare form extends to `zeebe:property` (Context 7), and the evaluation response reports the references an evaluation used (Context 9).

Together they are what makes this design possible rather than merely convenient. The third replaced a locally computed allow-list built by scanning property text and cluster-variable values: that approach over-matched — a regex decides that something *looks like* a reference, where the engine *knows* — and it could not see a reference past a truncated cluster-variable value, which failed closed but silently. The first turned the embedded form of Decision 5 from an unsupported case into an ordinary one. The second moves the failure for a mis-authored reference from first activation to deployment, which is where it belongs.

**Not covered here.** The hybrid Connector Runtime keeps resolving secrets locally in this release, as the epic decided, since routing it through the orchestration cluster would defeat the point of keeping secrets self-hosted. Restricting which secrets an inbound connector may read stays with [#7730](https://github.com/camunda/connectors/issues/7730). Note the asymmetry this creates, deliberately: the new form is gated by what the engine reports, while `{{secrets.X}}` and bare `secrets.X` stay unrestricted on inbound as they are today. (Superseded by Amendment 2: #7730 has since landed and the legacy forms are filtered on inbound too.) Making element templates emit the new form (Context 3) is separate work.

## Consequences

### Positive

- Secrets in the new form work for inbound connectors and configuration validation, which nothing else covers and no engine change will.
- No code is written that is expected to become dead. The engine keeps sole ownership of job activation.
- A secret value is never sent to the cluster as expression source, so it is never written into the record of an evaluation request or its result.
- What may be substituted is decided by the engine's own parse, not by a regex over text. A reference is resolved because the evaluation reported using it, not because something in the result looked like one — so a webhook payload, an HTTP response body or a plain `JSON` cluster variable containing reference-shaped text stays literal.
- Scoping that decision to one evaluation means a secret legitimately named by one property cannot be substituted into another property's value.
- The runtime derives nothing about secrets from storage: no cluster-variable search, no exported-projection lag, no truncation blind spot, and no requirement that secondary storage be present.
- A reference works the same whether it stands alone or sits inside a larger expression, so `Bearer {{secrets.TOKEN}}` has a direct equivalent and migrating it does not hit a wall.
- Exactly one place in the runtime substitutes a secret value. Two registration points feed it, and both cover the fields that actually hold credentials — including map values and list elements, which a property-level annotation cannot reach.
- Resolution costs one round trip per evaluation that uses secrets, batched, rather than one per secret; an evaluation naming no secret costs nothing extra.
- The public SDK is unchanged, so third-party secret providers keep compiling and behaving as before.
- The two forms no longer overlap in text, and the set of secrets the outbound allow-list permits is unchanged for existing processes.
- Inbound and the job path take the reference in the same shape, so what a modeller writes does not depend on which kind of connector reads it.
- Secrets held in `SECRET_REFERENCE` cluster variables work for configuration validation and inbound alike, which is what the credentials work needs — without the runtime having to reimplement the engine's rule about which variable kinds may hold references.
- If the outbound path does need covering later, it is a small addition on top of this, not a redesign.

### Negative

- **The secret-name charset must stay in step with the engine's.** `SecretReferenceUtil.PATTERN` is `camunda\.secrets\.(?<secret>[\p{Alnum}_-]+)`, matching the engine's charset since [camunda/camunda#60446](https://github.com/camunda/camunda/pull/60446). The dash in that charset is a name character, not an authoring one: FEEL reads a bare dash as subtraction, so `db-password` is only ever written ``=camunda.secrets.`db-password` `` in a model, while the placeholder the engine emits, the resource id a `SECRET:REVEAL` grant names and the text this pattern locates in a result are all the unescaped `camunda.secrets.db-password`. A model that writes the unescaped form does not reference the secret at all — it subtracts — and until the engine's deploy-time validator for that lands it fails at evaluation rather than at deployment. If the two ever diverge again, a name the cluster reports is simply not located in the result, so the secret silently fails to substitute. It fails closed — the placeholder survives and the connector fails visibly rather than binding a wrong value — but nothing in the build catches the mismatch, because the engine's test for it cannot see this repository.
- **The runtime's account must hold a `SECRET:REVEAL` grant.** Without it the resolve endpoint refuses every reference and nothing resolves. Granting it is an upgrade step that has to be documented for Helm and Console, not something the runtime can arrange for itself.
- **There are now two ways to write a secret, and both stay.** They differ in syntax, in where values come from, in how they are configured and in how they fail. Maintainers have to know why they deliberately do not mix, and users have to know which one their store is set up for.
- **Within one evaluation, substitution is not positional** (Decision 15). An expression that references a secret and also carries attacker-influenced data can leak that one secret into the data. Bounded, but real, and not closable at this layer.
- **Secrets in the new form do not work for outbound connectors until the engine's own job-push work ships.** This is the deliberate bet in Decision 1; if it slips, we cover that path after all.
- **A reference in the new form cannot be satisfied locally.** Keeping the forms apart means no environment variable will do, so local development and tests need either a configured store or a stand-in for the cluster.
- **Nothing resolves against a cluster that does not report referenced secrets.** The behaviour is safe — placeholders survive, and the first unreported reference logs a warning — but the client reports an absent list and an empty one identically, so the runtime cannot detect an incompatible cluster at startup and say so once, up front.
- **A missing grant reads as "secret not available".** Treating all failures alike is far less code, at the cost of a misleading message; the per-reference log naming the real cause makes it findable but does not fix it.
- **Secret values substituted into inbound properties are not hidden from error output**, because inbound never hid them. This does not make that worse, but it does make the gap reachable by a second route.
- **Every plain string property on the inbound binding path is now inspected.** The check is a cheap prefix test, but the consequence is a behaviour change: a plain-string field whose value begins with `=` and names a reference is now sent for evaluation, where before it was bound as text.
- **Configuration validation no longer accepts the legacy syntax at all.** That is deliberate (Decision 13) and the surface is unreleased, but it means the two entry points to credentials do not accept the same syntax as each other.
- **We depend on an unfinished API.** The client commands and both endpoints are marked experimental and open to change, so a client update could break this. Treating failures as described in Decision 11 bounds the worst case to secrets not resolving, rather than the runtime failing to start.

## Amendment 1: a legacy secret name may fall back to the central store

Decision 2 above keeps the two forms apart in both directions: neither falls back to the other when it comes up empty. That is reversed in one direction, under an explicit opt-in.

`camunda.connector.secret-resolver.legacy.mode` takes three values. `ON` is the default and is the behaviour Decision 2 describes. `OFF` stops legacy references resolving at all, so a model still using the legacy syntax fails naming the setting rather than binding an unresolved placeholder as a credential. `FALLBACK` looks a legacy name up in the orchestration cluster's secret stores as `camunda.secrets.<name>` when no configured provider holds it.

**Why the reversal.** Decision 2's reasoning — that a value's origin should be unambiguous — holds, and is the reason this is not the default. But without a fallback there is no incremental migration: every diagram referencing a secret has to be edited in the same change that moves the value into the central store. With it, a deployment moves values one at a time, drops the local provider, and existing diagrams keep resolving. The ambiguity Decision 2 avoids is bounded by the mode being chosen deliberately, per deployment, and by the fallback sitting last in the provider chain, so a name a configured provider still holds keeps coming from there.

**Never inferred.** `ON` is the default, so nothing has to be set to keep today's behaviour; what has to be set explicitly is the fallback. It is deliberately not derived from "no secret provider is configured", because a provider reading the environment is registered by default and so that condition is never actually met; inferring the fallback from it would change behaviour for every existing deployment.

**Paired with a strict secret filter.** The fallback lets the legacy syntax reach the cluster's secret stores, and on the outbound job path the only thing keeping a legacy reference that arrived in a *runtime value* from resolving is the outbound secret filter. Its allow-list is drawn from the element's input mappings in the deployed model while replacement runs over the job's variables, and that asymmetry is the whole protection: a name a variable carries resolves only if the model declares it too. That filter ships strict by default, but its lax setting resolves everything whenever the process-definition lookup fails, and it can be disabled outright. The runtime refuses to start on `FALLBACK` unless the filter is strict, so the pairing is a code invariant rather than a runbook step.

What the filter does not do is restrict which secrets a *model* may name: an input mapping spelling out `secrets.ANY_NAME` puts that name on its own allow-list, so a deployed model reads it under `STRICT` exactly as it would without the filter. That is what makes the guard's outbound-only scope acceptable rather than a hole. An inbound connector's `SecretFilter` is unconditionally allow-all (Decision 2, "not covered here"), but legacy replacement there only ever runs over the element's own `zeebe:property` text, read from the deployed model, and never over a runtime value — an evaluation result is data and is never fed back through replacement. So the two sides coincide, and an inbound allow-list derived from the model would be the same set as the text it filters. `FALLBACK` therefore extends what an inbound legacy reference can reach from the configured local providers to the cluster secret store, but no further in name than what a deployed outbound model reaches under `STRICT`. What remains is a difference of enforcement rather than of reach — outbound the restriction is a list the runtime checks, inbound it holds because of where the call sites read from — and one of failure mode: outbound `STRICT` also fails closed, failing the job when the allow-list cannot be loaded, where inbound has no list and so nothing to fail on. [#7730](https://github.com/camunda/connectors/issues/7730) would wire a filter into the inbound path and make it checked there too; it is open and unstarted, and `InboundSecretReferenceBindingTest` pins the property in the meantime. (Superseded by Amendment 2: it has since landed, so the inbound filter is no longer unconditionally allow-all and inbound now does have a list.)

**Residual risk, accepted.** The two forms then reach the same store with protections of different strength. The new form's allow-list is always on and sits directly in the resolution path (Decision 4); the legacy form's protection is the secret filter, which is configuration. Narrowing the grant to only the migrated names would have made this structural, but on SaaS the runtime holds one `SECRET:REVEAL` grant covering the whole store, so that option does not exist. The startup guard is the mitigation.

**Names that cannot migrate.** The reference charset is narrower than the legacy secret-name charset, which admits `.` and `/`. A legacy name outside the reference charset has no reference form, so the fallback cannot read it; the lookup fails saying exactly that, rather than reporting the name as merely unavailable. Such a name has to be renamed, which also means editing the diagrams that use it. This affects self-managed deployments only: Console has always restricted connector secret keys to the same characters the reference charset allows.

**A cluster that cannot be reached is not a missing secret.** The fallback resolves strictly: a resolve request that fails outright propagates, while a reference the cluster declined with a definitive answer stays absent. Definitive means the stores were read and this reference will not resolve however often it is asked for: `NOT_FOUND`, `ACCESS_DENIED`, `INVALID_REFERENCE`. The other per-reference answers propagate like a failed request, because they do not say the secret is missing — `UNREADABLE` says a store holds the name and reading its value failed, and a code this runtime cannot map says nothing at all. The cluster's own enum is only guaranteed to be handled exhaustively by callers released from its repository, which this runtime is not, so the runtime keeps an allow-list of the definitive codes rather than a list of the failing ones: a code it has never heard of, or an error carrying none, fails by construction. A store-wide outage never reaches this classification — the cluster fails the whole request rather than reporting every reference as missing — so what this covers is the narrower per-secret read failure. The two have to be distinguishable because the caller does not treat them alike — an unresolved legacy name becomes a `ConnectorInputException`, which fails the job without retrying, so reporting an unreachable cluster as a miss would raise a permanent incident over a network blip. The exception the strict path raises is deliberately neither a `ConnectorInputException` nor caused by one, since that type is what the runtime reads as "the input will never bind". It also carries neither a cause nor the client's own message, which can echo the response body.

The same distinction protects error masking. Masking works by re-resolving the secrets named in a job's input and redacting those values from the message; a fetch that silently returned a short list produced a message redacted only in part, and an error that echoes a credential back would then reach process variables. Strict resolution makes that fetch fail rather than under-redact, and both places that perform it withhold the message they cannot redact instead of publishing it.

A short list is refused on the same grounds, not only a failed fetch: the re-read has to come back with a value for every legacy name the input declares, or the message is withheld. That requirement is exactly as strong as the replacer's, which fails a binding when a provider returns null for a name the filter allows — so the input cannot have been bound unless every legacy name it declares resolved, and one missing on the re-read means the secret was removed, or access to it revoked, while the connector ran. It is required of the legacy names only. The new form is asked for as well, but neither required back nor allowed to fail the read, because on the job path it can hardly ever contribute: the engine substitutes a reference in a job's variables before activation (Context 1), so a reference the masking scan can still see is one the engine did not substitute — the connector held placeholder text, and no value of that secret is in the message. Requiring it back would withhold the error message of nearly every failed job using the new syntax, and letting its fetch failure propagate would withhold the message of a job whose legacy secrets all read back fine.

**An engine-substituted value is not redactable, and none of this changes that.** Where the engine did substitute, no reference is left in the variables for the masking scan to find, so the value is absent from the redaction list and a connector that echoes it into an error message publishes it. An activated job carries no record of the references it was resolved from, and Decision 1 leaves the job path to the engine, so there is nothing in the runtime to derive the name from; the only rule that would cover the case is withholding every outbound error message, substituted or not. Recorded as a limitation rather than fixed.

**Measuring the retirement.** `camunda.connector.secret.legacy.resolutions` counts how often a legacy reference actually resolves, per orchestration cluster, so that retiring the legacy syntax can be decided on evidence. The same three-state setting can back a customer-facing switch once a deployment has finished migrating: flipping it early fails loudly rather than silently binding placeholders.

## Amendment 2: the inbound secret filter is now enforced, and it is not a no-op

[#7730](https://github.com/camunda/connectors/issues/7730) has landed, so two statements above are no longer current: an inbound connector's `SecretFilter` is not unconditionally allow-all (Decision 2's "Not covered here", and Amendment 1's "Paired with a strict secret filter"), and the legacy forms are no longer unrestricted on inbound. `camunda.connector.secret-resolver.secret-filter.mode` now governs both directions. `DISABLED` restores the previous allow-all behaviour; `LAX` and `STRICT` both enable the filter and are identical inbound, because the allow-list is computed from data already in memory and so has no lookup that can fail.

**Correction: the reasoning above was wrong about there being nothing to reject.** Amendment 1 argued that legacy replacement on inbound only ever runs over the element's own `zeebe:property` text, so the two sides coincide and an allow-list derived from the model would be the same set as the text it filters. That is true of the *input* to `SecretUtil.replaceSecrets`, and false of what the function actually filters. It runs the brace pass, then runs the bare pass **over that pass's output** — text which by then has resolved secret values spliced into it. A secret whose value contains reference-shaped text therefore produces a second-order lookup for a name no model declares, and under `FALLBACK` that name is looked up in the cluster's secret stores. Where a value is attacker-influenced or simply careless, one secret can pull in another.

So the filter is not defence in depth against a hypothetical future call site; it closes a present-day escalation, at both inbound call sites (`getProperties`/`bindProperties`, and `bindProperties` on a correlation result). Verified both as a unit — filter off resolves the chained name, filter on leaves the placeholder — and against a live cluster, where the same diagram flips BASIC auth between 200 and 401 on nothing but the mode setting. An earlier probe that reported all four modes behaving identically had not exercised a chained value, and this document repeated that conclusion; both were wrong.

**This decides the scope of the allow-list.** It is derived per call from the exact property text that call is about to filter, not from the executable's elements as a whole. Deriving it from the union across sibling elements — which a single executable has whenever a deduplication scope lets grouped elements differ on out-of-scope properties, as the webhook connector's does — would let a chained value reach any secret any sibling names, which is precisely the reach this is meant to deny.

**Correction: "declared in that text" is not the same as "declared in a form this filter's own resolver reads."** The allow-list is extracted with `retrieveLegacySecretKeysInInput`, not `retrieveSecretKeysInInput`. The latter also matches the new `camunda.secrets.<name>` form — deliberately, per Decision 12, so the *outbound* allow-list does not shrink when a model migrates syntax. Reusing it here would have let a name declared only in the new form onto an allow-list that gates `SecretHandler.replaceSecrets`, which never resolves that form at all (Decision 2 keeps the two forms apart in both directions). A chained value naming that same name in legacy syntax would then resolve it through the local provider chain — a mechanism the model's new-form reference never invoked and was never authorized for. Outbound's use of the wider method is unaffected by this and remains correct: there, the model is already unconditionally trusted to put any name on the allow-list in any form, so which form it used was never the boundary that mattered. Inbound's boundary is the resolution mechanism itself, so the extraction has to match the resolver it feeds, not merely the model text it feeds it from.

**It also removes a failure direction rather than adding one.** While the filter was allow-all it could not deny anything. An allow-list drawn from the executable's model would have introduced denials, because a live executable's model is mutable: `updateConnectorDetails` swaps its elements in place when a new process version is hot-swapped onto it, so a list read at a different moment than the text it judges can refuse a secret that text itself declares. Deriving the list from the text in hand makes that unrepresentable — there is no second, separately-timed piece of state to disagree with.

The general lesson is not that a structural guarantee is cheap to make enforced, but that the guarantee has to be stated about the right thing. "Replacement only sees model text" was asserted of a function that feeds its own output back through itself, and neither the original decision nor the first amendment checked that.

## Amendment 3: the startup guard pairing `FALLBACK` with a strict secret filter is removed

Amendment 1's "Paired with a strict secret filter" made the pairing a code invariant: the runtime refused to start under `FALLBACK` unless `camunda.connector.secret-resolver.secret-filter.mode` was `STRICT`. That guard is removed.

**Why.** `STRICT` is a breaking change for a diagram whose legacy references the filter's allow-list does not cover — see Decision 2's asymmetry and Amendment 2's extension to inbound. A deployment that hits this needs a way to keep running while it fixes the affected diagrams. Refusing to start denied it, forcing an operator to choose between reverting the legacy mode away from `FALLBACK` altogether and being unable to migrate incrementally, or fixing every diagram before restarting at all.

**`LAX` is not the escape hatch; `DISABLED` is.** `LAX` applies the same allow-list as `STRICT` whenever that list loads successfully — outbound it only permits everything when the process-definition lookup itself fails, and inbound it is unconditionally identical to `STRICT` (Amendment 2), since the inbound list is computed from data already in memory and has no lookup to fail. A legacy reference the allow-list would reject under `STRICT` is rejected under `LAX` too, as long as the list loads. Only `DISABLED` removes the check outright, so it is `DISABLED` an operator pairs with `FALLBACK` to keep a diagram's rejected reference resolving while fixing it, not `LAX`.

**What was traded away.** The residual risk Amendment 1 accepted — the two forms reaching the same store with protections of different strength — is no longer bounded by the runtime refusing to start; it is now a deployment choice. An operator who sets `FALLBACK` with `DISABLED` gets exactly the reach Amendment 1 warned about, deliberately, for as long as the migration takes.

## Amendment 4: replacement no longer feeds its own output back through itself

[#8602](https://github.com/camunda/connectors/issues/8602) replaced `SecretUtil`'s two passes with a single left-to-right scan over one pattern holding all three reference forms. A resolved value is no longer rescanned, so the second-order lookup Amendment 2's correction describes — a secret whose value contains reference-shaped text producing a lookup for a name no model declares, reaching the cluster's stores under `FALLBACK` — no longer exists. It is closed at its source rather than denied by the filter.

**What this does and does not change about the filter.** Amendment 2's conclusion that the inbound filter closes a present-day escalation was true of the code it was written against, and the escalation it named is now gone. The filter is not thereby a no-op: it still refuses a name only a sibling element declares (the reach Amendment 2 decided the allow-list's scope to deny), and any name in text a caller supplies rather than the element's own properties, since `SecretHandler.replaceSecrets` is reachable with arbitrary text. `secretFilterEnabled_leavesASecretNamedOnlyByAnotherSecretsValue` still passes, but for a different reason than when it was written — nothing rescans the value, so the filter is no longer what stops it. Outbound is untouched: the allow-list still comes from the model while replacement runs over job variables, and `STRICT` still fails closed there. Amendment 3 has since removed the startup guard that paired `FALLBACK` with `STRICT`, so the residual risk that amendment consciously accepted is now smaller by exactly this escalation: an operator pairing `FALLBACK` with `DISABLED` still gets the reach Amendment 1 warned about, but a resolved value can no longer name a further secret and pull it from the cluster's stores.

**The lesson Amendment 2 drew was right, and this is the other half of it.** That amendment observed that "replacement only sees model text" had been asserted of a function that fed its own output back through itself. The function no longer does — and, more to the point, the allow-list extractor and the resolver now read text with one shared scan, so "the names extracted are the names resolved" is a property of the code rather than a claim about it. The same two-pass split also silently admitted a truncated prefix of any name outside the bare form's character class (`FOO` from `{{secrets.FOO:BAR}}`) onto the outbound allow-list, and cost a quadratic rescan of every denied reference in a job's variables; both were consequences of reading the same text more than once, and both are gone with it.

## Amendment 5: the allow-list is scoped by field path, not by name alone

Every mention of "allow-list" and "declares" above, on both sides, described a set of secret *names*: a legacy name declared anywhere in an element's input mappings (outbound) or property text (inbound) was allowed to resolve anywhere in that same element. That is no longer accurate. `SecretFilter.Secret` now carries a `fieldPath` alongside the secret name, and `SecretFilter.allowOnly` matches a lookup only when the name matches **and** the declared path is a prefix of the path the lookup is running at. A name declared under `authentication.token` no longer authorizes a lookup under an unrelated field such as `notes`, even on the same element.

**Why name-only was too wide.** `SecretUtil.replaceSecrets` walks a `JsonNode` tree rather than a raw string, so it already knows, for every substitution, exactly which field it is substituting into. Discarding that path down to a flat name-only allow-list threw away information the walk had for free, and let a secret declared on one field resolve on any other — including a field an attacker-influenced value could point at, on either side of the runtime/inbound boundary Amendment 2 discusses.

**The declared path is a prefix, not an exact match.** A field path is derived statically — from a `zeebe:input`'s dotted `target`, or an inbound `zeebe:property`'s dotted key — but the value an input assembles at runtime can nest a FEEL context/object expression under that path, one or more levels deeper than the static declaration. `SecretFilter.allowOnly` therefore allows a lookup whenever the declared path is a prefix of the lookup's own path (an empty declared path is the wildcard case, matching every path, which is what the inbound side used before this amendment and what a handful of call sites with no tree to scope against — e.g. the outbound `JobHandlerContext` allow-all path — still use deliberately). It never matches the other way: a name declared at the deeper path `foo.bar` does not authorize a lookup at the shallower `foo`.

**Outbound: propagation follows FEEL data flow, not just declaration.** A template commonly assembles one input's value from another — `url = "=baseUrl + \"/services/apexrest/\" + path"` reading a `baseUrl` input that itself holds a secret. `ProcessDefinitionSecretKeyCache.extractSecrets` parses each input's FEEL expression (`org.camunda.feel.api.FeelEngineApi`, parse only, no evaluation) and builds a dependency graph among the inputs of one `zeebe:ioMapping`: a secret declared on one input is also allowed on every input whose own expression references the variable the declaring input's target writes, transitively. A referenced path matches a candidate's target by prefix in either direction, not by comparing only their first segment, so that two sibling fields sharing a top-level name (`authentication.type` and `authentication.token`) are not treated as depending on each other merely for that.

**The dependency graph respects declaration order and shadowing.** `zeebe:input` mappings evaluate in declaration order, each against the output the ones before it already built; a later mapping's target is invisible to an earlier one, so only a *preceding* input can be a dependency, never a following one. A target written more than once is reachable only through its nearest-preceding writer, and a later write to a parent path (`authentication = {...}`) invalidates every earlier writer of a path beneath it (`authentication.token`), since the parent write replaces that whole subtree — and this invalidation covers both a writer's own grant and any grant it would otherwise have propagated to a dependent input, since neither is meaningful once something else is what the runtime field actually holds.

**Shadowing cuts both ways, and the narrower direction fails closed.** The mirror case is a later write to a *child* of a path a secret was declared on (`authentication = secrets.WHOLE` followed by `authentication.token = someVariable`). Because a grant is a path *prefix*, the declared path `authentication` also authorizes a lookup at `authentication.token` — the one field the later mapping controls — so a placeholder in that later, potentially process-controlled value would resolve a secret it never carried. A prefix cannot express "everything under `authentication` except `.token`", so an input with any later writer beneath its own target grants nothing at all: not at its own path, and not propagated to the inputs that read it (which would otherwise copy the shadowed subtree one hop further). This is deliberately wider than strictly necessary in one shape — a parent whose own FEEL object nests its secret under a field the later mapping never touches (`authentication = {user: "{{secrets.USER}}"}` alongside `authentication.token = ...`) loses a grant that was legitimate for `authentication.user`. That over-denial is accepted: unlike the over-approximation below, the failure direction here is a secret that stops resolving, not one that resolves where it should not, and narrowing it further would require the filter to know each input's effective write scope rather than a single declared prefix.

**Accepted over-approximation: a reference is treated as carrying the secret, not proven to.** Propagation triggers on any FEEL reference to the declaring input's target, including one reference among many in a larger expression (`="prefix-" + baseUrl`) — the same shape Context 5 and Decision 15 already accept on the new-form side. No attempt is made to prove the assembled value actually retains the secret's text (a transformation could in principle drop or alter it); the grant is therefore occasionally wider than strictly necessary, in exchange for not requiring real dataflow/taint analysis over arbitrary FEEL. This mirrors the pre-existing outbound stance in the Consequences section below: the model is trusted to name what it needs, and the allow-list follows that trust rather than second-guessing it.

**Inbound gets the same field-path model.** `InboundConnectorContextImpl#declaredSecretNames` now derives each secret's path from the declaring `zeebe:property`'s own (dotted) key, matching the path `InboundPropertyHandler#readWrappedProperties` gives that same key once nested — the path a leaf occupies when `SecretUtil.replaceSecrets` walks the wrapped property tree at resolution time. This replaces the empty-path wildcard Amendment 2 introduced (every declared name allowed everywhere on the element), closing both a sibling-field leak and a same-field-different-sibling chained-resolution path: a value that resolves to text naming a secret declared only on an unrelated field can no longer pick it up merely because both fields belong to the same element.

**Outbound's allow-list is scoped to the legacy forms alone.** `extractSecrets` derives each input's own secret names with `retrieveLegacySecretKeysInInput`, not the wider `retrieveSecretKeysInInput` Decision 12 describes — that method's inclusion of the new `camunda.secrets.<name>` form exists for a masking scan over data already in hand (Amendment 1's "asked for as well, but neither required back nor allowed to fail the read"), not for building an allow-list that gates `SecretHandler.replaceSecrets`, which never resolves that form at all. Reusing it here would have let a name declared only in the new form authorize a legacy-syntax lookup of the same name — the two forms reaching the same store by a path neither Decision 2 nor Amendment 1 intended, since the new form was never meant to reach the legacy providers at all, `FALLBACK`'s explicit crossing in the other direction notwithstanding. This mirrors the correction Amendment 2 already made to the inbound extraction, and removes the one masking-path read that method's wider form still fed: it could return only a name a legacy declaration didn't already cover, which the same tightened allow-list now forecloses, so that read no longer had anything to contribute.
