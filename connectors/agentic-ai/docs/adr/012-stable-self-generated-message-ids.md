# Stable, self-generated conversation message ids

* Deciders: Agentic AI Team
* Date: August 13, 2026

## Status

**Implemented**

## Context and Problem Statement

Conversation messages have no independent identity of their own. One message type carries a
provider-sourced id, but it's populated by whichever provider integration happens to set it,
isn't guaranteed to exist, and today is only ever consumed for one storage backend's round-trip —
it was never meant as a general-purpose identity mechanism, and the other message types have no id
at all.

The agent instance history API is being redesigned (camunda/camunda#58789) to support correlating
and deduplicating history items by id — see the companion decision on streaming tool call results
into history as they arrive, whose duplicate-write tradeoff this id is meant to eventually
resolve. To be ready for that, every message needs a stable id of its own, generated by the
connector rather than borrowed from a provider that may not supply one.

## Decision Drivers

* **Coverage**: every message type needs an id, not just the ones a provider happens to populate.
* **Stability**: once assigned, an id must not change across reloads of the same persisted
  message — dedup depends on it being the same value every time.
* **Minimal surface area**: avoid new persisted state beyond the id itself; avoid a parallel
  migration mechanism if the existing serialization contract can absorb the change.
* **Non-null domain model**: this module's convention is non-null-by-default; a field that's
  sometimes absent should either be explicitly nullable or handled so the domain type never has to
  represent "no id" as a real state.
* **No new identity for tool-call correlation**: the existing tool-call id (used for engine-side
  element activation and the provider round-trip, where a tool result must echo back the exact id
  the provider issued) must not be touched by this change. This is distinct from the message-level
  id every message gets under this decision — including the message that wraps a batch of tool
  results — which identifies the message, not the tool call.

## Considered Options

| Dimension | A — random id, generated once, persisted forward | B — deterministic id, re-derived from position |
|---|---|---|
| Generation | Random, at first construction | e.g. derived from turn/role/index |
| Stability mechanism | Persistence (write once, read back unchanged) | Recomputation (same inputs always yield same id) |
| Retry/duplicate-write behavior | Two independently-constructed copies of "the same" message get *different* ids | Two independently-constructed copies get the *same* id automatically |
| Complexity | Needs the id to flow through construction, persistence, and reload, but no derivation logic | Needs every construction site to know its own position/scoping correctly, including edge cases |
| Fit with existing per-item identity | Coexists with the existing tool-call correlation id (already stable) without overlapping it | Same |

## Decision Outcome

**Option A** — a random id, generated once, stable via persistence, not re-derivation.

- **Every message type gets an id**, one per message instance. Not pushed down to the individual
  results inside a batched tool-result message — those already have a stable identity via the
  existing tool-call correlation id, and duplicating it with a second random id would be
  redundant.
- **The existing tool-call correlation id is untouched.** It keeps meaning exactly what it means
  today and remains the correlation key for engine-side element activation and the provider
  round-trip.
- **The existing provider-sourced message id is untouched too, but its documentation was
  wrong.** It's populated by more than one provider integration's response handling, not just the
  one storage backend that historically consumed it — but that storage backend is still the only
  place it's ever read back today. We keep it separate from the new id rather than merging the
  two: the new id is a synthetic, always-connector-generated dedup key; the provider-sourced field
  is a provider-relation key, useful if we ever need to correlate back to a specific provider
  response. The two coexisting costs a few extra bytes per message — accepted, since collapsing
  them would conflate two identities with different lifetimes and different owners (us vs. the
  provider).
- **Generation mechanism**: each message type defaults its id to a fresh random value whenever one
  isn't explicitly supplied at construction. This means:
  - Building a message without setting an id generates a fresh one inline.
  - Deserializing persisted data that already has an id binds that exact value, so the id survives
    every store/reload round trip unchanged.
  - Deserializing **pre-existing** persisted data that has no id at all leaves it unset, so the
    same default fires and mints a fresh id at load time — backfill-on-load falls out of the same
    mechanism used for fresh construction, with no separate migration step. The domain model stays
    non-null throughout.
- **Which id a future history item carries depends on its role — this is not uniform.** A
  message that maps one-to-one to a history item (e.g. a user or assistant message) carries that
  message's id. A message that batches multiple tool results, however, already maps to multiple
  history items today — one per result — so a single parent-message id would collide across all of
  them and defeat per-item dedup. Those items keep using the existing per-result correlation id
  instead, unchanged by this decision.
- **No plumbing added anywhere the id has nowhere to go yet.** The agent-instance-reporting layer
  already receives the full message objects it needs, so they carry the new id the moment this
  ships, with no interface change required. Threading the id further down into the wire-level
  history-item call would add a parameter nothing reads today — the current wire API has no field
  to receive it — so it would only be dropped at the bottom. When the redesigned API lands, only
  that layer's internals change to thread the id through; the interface contract stays stable.
- **The AWS AgentCore conversation store needed an explicit fix**, since it doesn't serialize
  messages the same way the other two stores do — it hand-reconstructs messages from that
  platform's own event format instead of going through the standard serialization path, and had no
  notion of id at all before this change. Every reload would otherwise have minted a fresh one,
  silently breaking the stability guarantee for that one store. Fixed by carrying the id through
  that store's own event properties, symmetrically with how other provider-specific fields already
  round-trip there.

### Positive Consequences

- Every message carries a stable, connector-owned id regardless of provider, with no reliance on
  provider-supplied identifiers that may be absent.
- Backfill for pre-existing persisted conversations is free — the same default-generation
  mechanism that mints a fresh id on construction also covers "id missing from old data," with no
  additional migration surface.
- The domain model stays non-null, consistent with this module's conventions.

### Negative Consequences

- A message built more than once outside of persistence (e.g. two independent in-memory
  constructions intended to represent "the same" logical message) gets a *different* random id
  each time — not useful for deduplicating that specific case. Stability only holds once a message
  has actually been persisted and reloaded.
- Backfilled ids for pre-existing conversations are not reproducible: reloading the same
  not-yet-persisted-with-this-change message twice, before it's ever written back to the store,
  mints two different ids. In practice this window is narrow — the id becomes stable as soon as
  the conversation is next stored.
- The AWS AgentCore store's own historical data (events written before this change, by its
  append-only write path) can't retroactively acquire a durable id either: a backfilled id for one
  of those is minted fresh on every load, the same as any other backfill, but this store's write
  path never rewrites already-written history to persist that backfilled value going forward.
  Accepted for now — that store has not shipped in a stable release, so there is no real
  historical data at risk in practice. Worth a proper fix (e.g. an explicit backfill write, or
  deriving an id from that platform's own stable event identity) before this store is considered
  production-ready independent of this ADR.

## Out of Scope

- Threading the id through to the wire-level history-item call — the current API has no parameter
  for it; this lands only once the redesigned agent instance history API supports it.
- Any change to the existing tool-call or per-result correlation ids — both remain exactly as they
  are today.
- Deterministic/re-derived ids (rejected Option B above).
- A durable fix for AWS AgentCore's historical (pre-this-change) data — see Negative Consequences.
- Choosing a specific id format (e.g. a time-sortable variant) over a plain random one — postponed;
  revisit if storage-backend index locality becomes a real concern.
